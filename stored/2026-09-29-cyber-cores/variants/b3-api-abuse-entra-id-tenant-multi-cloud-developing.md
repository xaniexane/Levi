# Public API Abuse Defense for Microsoft Entra ID Tenants in Multi-Cloud (Developing Maturity)

## Purpose

Exposed APIs are probed for injection, broken auth, and excessive data exposure. API abuse looks like legitimate traffic at volume — detection needs API-aware logging (endpoint, parameters, auth context), not just web logs. Applies to Microsoft Entra ID Tenants in Multi-Cloud at Developing maturity.

## When to use

- High-rate 4xx/5xx sequences against API endpoints indicating fuzzing, or single clients enumerating object IDs sequentially.
- Authenticated API calls accessing other users' objects (BOLA/IDOR patterns) or returning bulk data far beyond normal use.
- Known attack strings (SQLi, SSTI payloads) in API parameters.
- Lens: Best telemetry: Entra sign-in + audit logs streamed to Log Analytics/SIEM with 30+ day retention. Cloud-agnostic SIEM normalizing AWS CloudTrail, Azure Activity Log, and GCP Audit Logs into one schema.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to CSPM coverage across all clouds with consistent misconfiguration alerting.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Sign-in logs (interactive, non-interactive, service principal) with risk detections and MFA details and Audit logs: app registrations, consent grants, Conditional Access changes, role assignments; run `# Microsoft Graph (delegated admin): recent risky sign-ins` then `Get-MgAuditLogSignIn -Filter "riskState eq 'atRisk'" -Top 25 | Select-Object CreatedDateTime, UserPrincipalName, IpAddress, @{n='Risk';e={$_.RiskDetail}}`.
3. **Analyze.** Replay the suspect API sessions to determine exactly which records were accessed — the breach scope is the data returned, not the requests made. Then: Check whether the abused endpoint lacks authorization checks versus a credentialed attacker using stolen tokens.
4. **Contain and harden.** Positive-security API gateway policies: schema validation, rate limits per client, and authorization checks on every object reference. Asset layer: Conditional Access: require phishing-resistant MFA, compliant devices, block legacy auth and risky sign-ins. Environment layer: Federated identity across clouds from one IdP; consistent tagging and logging standards per cloud.
5. **Document and improve.** Assign RACI for each procedure step (who detects, who contains, who communicates) and rehearse it quarterly. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- WAF-only defense: most API abuse is semantically valid HTTP that no signature catches.
- Logging without the auth context — you cannot distinguish attack from customer without knowing WHO called.
