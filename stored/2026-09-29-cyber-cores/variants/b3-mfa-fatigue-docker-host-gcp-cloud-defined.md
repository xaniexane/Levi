# MFA Fatigue Attack Defense for Docker Hosts in GCP Cloud (Defined Maturity)

## Purpose

Attackers with a stolen password spam push notifications until the victim approves one out of annoyance or confusion. The defense is push hygiene: number matching, context display, and rate limits on prompts. Applies to Docker Hosts in GCP Cloud at Defined maturity.

## When to use

- Dozens of MFA push prompts to one user in minutes, especially at odd hours, followed by a single approval.
- An approval immediately followed by session activity from an unusual IP or device enrollment changes.
- Helpdesk reports of users 'getting lots of MFA prompts' in the days before the incident.
- Lens: Best telemetry: Docker daemon logs + host auditd + container stdout/stderr shipped centrally. Cloud Audit Logs (admin + data access) exported to a locked-down logging project.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to Security Command Center findings and VPC flow logs centralized.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Docker daemon log (container create/start with full flags), docker events history and Container image digests and layer histories (docker history) versus expected digests; run `docker ps --format '{{.Names}} {{.Image}}' ; echo ---; docker events --since 24h --until 0s 2>/dev/null | tail -20` then `docker inspect $(docker ps -q) --format '{{.Name}} privileged={{.HostConfig.Privileged}} mounts={{.Mounts}}' 2>/dev/null`.
3. **Analyze.** Reconstruct the prompt storm: count, timing, and the approving event — then inventory the attacker's post-approval actions. Then: Check whether the attacker registered a new MFA method during the session (persistence via second factor).
4. **Contain and harden.** Number matching on all push MFA, show login context (app, location), and rate-limit prompts per user. Asset layer: No --privileged, no host socket mounts except for explicit agents, user namespaces enabled, read-only root filesystems. Environment layer: Organization policies constraining public exposure, API enablement, and service-account key creation.
5. **Document and improve.** Map each detection signal to the relevant MITRE technique and confirm coverage in the detection engineering backlog. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Assuming an approved push means a legitimate user — approval is exactly what the attacker engineered.
- Not checking for newly registered MFA methods, which survive password resets.
