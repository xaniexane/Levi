# Firmware Rootkit Defense for AWS Accounts in Colocation Facilities (Optimized Maturity)

## Purpose

Malware in UEFI/BIOS or device firmware survives OS reinstalls and disk replacements. Rare but devastating — detection needs firmware measurement (TPM attestation) and dedicated scanning, not standard AV. Applies to AWS Accounts in Colocation Facilities at Optimized maturity.

## When to use

- CHIPSEC or firmware-scanner findings of modified UEFI modules, unexpected DXE drivers, or Secure Boot disabled without authorization.
- TPM attestation failures or PCR values deviating from the known-good baseline for the hardware model.
- Persistence surviving full disk wipe and OS reinstall — the hallmark symptom.
- Lens: Best telemetry: CloudTrail (org trail, all regions) + GuardDuty + VPC flow logs + Config. Customer-owned network taps and logging (the colo provider's logs are out of scope — verify contractually).

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to Badge/physical access logs from the facility correlated with remote-hand ticket times.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in CloudTrail event history (console logons, IAM changes, AssumeRole, security-group changes) and GuardDuty findings, IAM Access Analyzer results, and S3 server-access logs for data stores; run `aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=ConsoleLogin --max-items 20` then `aws iam generate-credential-report && aws iam get-credential-report --query Content --output text | base64 -d | head -5`.
3. **Analyze.** Dump the firmware image (with authorization) and diff against the vendor's known-good image for the exact board and version. Then: Determine the implant's capabilities: network, persistence mechanism, and whether it targets other hosts (some spread via firmware update mechanisms).
4. **Contain and harden.** Enable Secure Boot + TPM measured boot fleet-wide; lock BIOS with admin passwords and signed firmware updates only. Asset layer: MFA on root + all IAM users, SCPs denying logging disablement and unapproved regions, no long-lived keys. Environment layer: Locked cabinets, private cages, and escort policies for remote hands.
5. **Document and improve.** Feed incident lessons back into detection-as-code within one sprint — the playbook is a living document, not a PDF. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Reinstalling the OS repeatedly while the firmware implant re-infects each build.
- Running firmware scans from the potentially compromised OS — use offline/BIOS-level tooling.

## References

- MITRE ATT&CK: T1542 (Persistence: Pre-OS Boot: System Firmware)
- Vendor logging and hardening baselines for AWS Accounts; Locked cabinets, private cages, and escort policies for remote hands.
