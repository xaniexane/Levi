# DNS Fast-Flux Defense for Hyper-V Hosts in AWS Cloud (Optimized Maturity)

## Purpose

Fast-flux networks rotate DNS answers across many compromised hosts every few minutes, making malicious infrastructure hard to takedown. Defenders detect the flux pattern itself: low TTLs, high answer churn, and geographically scattered A records. Applies to Hyper-V Hosts in AWS Cloud at Optimized maturity.

## When to use

- DNS answers with TTLs under 300 seconds rotating across dozens of IPs in unrelated ASNs and countries for a single domain.
- Short-lived domains (registered days ago) resolving to residential or compromised-server IPs with no legitimate business relationship.
- Endpoint connections to flux domains correlating with malware detonations or phishing kit infrastructure.
- Lens: Best telemetry: Hyper-V-VMMS/Hyper-V-Worker event logs + host Security log + SCVMM job history. Organization CloudTrail in all regions, GuardDuty, and VPC flow logs shipped to the security account.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to CloudWatch and workload logs centralized; S3 access logging on sensitive buckets.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Microsoft-Windows-Hyper-V-VMMS event log (VM create/start/stop, checkpoint ops) and Virtual switch and virtual NIC configuration; VM configuration files and checkpoints; run `Get-WinEvent -LogName 'Microsoft-Windows-Hyper-V-VMMS-Admin' -MaxEvents 25 | Select-Object TimeCreated, Id, Message | Format-Table -Wrap` then `Get-VM | Select-Object Name, State, CheckpointType, @{n='Switch';e={(Get-VMNetworkAdapter $_).SwitchName}} | Format-Table`.
3. **Analyze.** Profile the flux: record TTL, unique IPs per hour, ASN/country spread, and name-server patterns to fingerprint the specific flux service or kit. Then: Pivot from the domain to find sibling infrastructure: shared name servers, registration patterns, and certificate overlaps.
4. **Contain and harden.** DNS response policy zones (RPZ) blocking confirmed flux domains, plus alerting on sub-300s TTL answers at the resolver. Asset layer: Dedicated management NIC/vLAN, Shielded VMs for sensitive workloads, guarded fabric where available. Environment layer: SCPs as guardrails (deny leaving org, deny disabling logging, region restrictions).
5. **Document and improve.** Feed incident lessons back into detection-as-code within one sprint — the playbook is a living document, not a PDF. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Blocking individual flux IPs — they churn in minutes; block the domain pattern and the detection logic instead.
- Confusing legitimate CDN behavior (low TTL, many IPs) with flux; require the ASN-scatter plus short-domain-age combination.
