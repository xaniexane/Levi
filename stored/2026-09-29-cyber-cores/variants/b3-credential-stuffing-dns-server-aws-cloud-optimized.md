# Credential Stuffing Defense for DNS Servers in AWS Cloud (Optimized Maturity)

## Purpose

Attackers replay username/password pairs stolen from third-party breaches against your login endpoints, betting on password reuse. It shows up as high-volume failed logons from distributed IPs, occasionally followed by a small number of successful takeovers. Applies to DNS Servers in AWS Cloud at Optimized maturity.

## When to use

- Authentication logs show a spike in failed logons (often 100s per minute) from many source IPs against a single login endpoint, with a low success rate and common password patterns.
- Successful logons immediately followed by password or MFA changes, mailbox rule creation, or impossible-travel alerts for the same account within minutes.
- WAF/bot-management flags distributed requests with identical user-agent strings, headless-browser markers, or known credential-stuffing tool signatures.
- Lens: Best telemetry: query logs (or passive DNS) + zone-transfer/change audit + resolver cache stats. Organization CloudTrail in all regions, GuardDuty, and VPC flow logs shipped to the security account.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to CloudWatch and workload logs centralized; S3 access logging on sensitive buckets.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in DNS query logs showing tunneling/DGA patterns; zone files and their change history and Zone-transfer (AXFR) request logs; DNSSEC validation failure logs; run `grep -E '.{60,}' /var/log/named/query.log | tail -20   # long labels: tunneling/DGA` then `rndc status; echo ---; journalctl -u named --since '1 hour ago' | grep -iE 'transfer|denied|error' | tail -15`.
3. **Analyze.** Separate spray from stuffing: stuffing reuses many passwords per username from breach corpora; confirm by checking whether the attempted passwords appear in public breach datasets. Then: For each successful post-stuffing logon, inventory session actions: read mail rules, forwarding addresses, OAuth grants, and API keys created in the 24 hours after compromise.
4. **Contain and harden.** Enforce MFA everywhere and block legacy/basic authentication; stuffing dies against phishing-resistant MFA. Asset layer: Restrict recursion to internal clients, block outbound port 53 except resolvers, DNSSEC validation on. Environment layer: SCPs as guardrails (deny leaving org, deny disabling logging, region restrictions).
5. **Document and improve.** Feed incident lessons back into detection-as-code within one sprint — the playbook is a living document, not a PDF. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Blocking single IPs is whack-a-mole against botnets; block on behavior (velocity, fingerprint) rather than address.
- Forcing a fleet-wide password reset without confirming which accounts were actually taken over burns goodwill and teaches users to pick weaker passwords.
