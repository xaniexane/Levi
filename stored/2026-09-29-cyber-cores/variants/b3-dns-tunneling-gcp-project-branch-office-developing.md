# DNS Tunneling Defense for GCP Projects in Branch Offices (Developing Maturity)

## Purpose

DNS tunneling smuggles data or C2 inside DNS queries, abusing a protocol almost every network allows outbound. Detection hinges on query shape (length, entropy, volume, record types), not on blocklists. Applies to GCP Projects in Branch Offices at Developing maturity.

## When to use

- Long, high-entropy subdomains (often 50+ chars) in DNS logs, unusual record types (TXT, NULL) at volume, or a single host generating thousands of queries to one domain.
- Beacon-like regularity in query timing to an obscure domain, or DNS queries for domains registered within the last 30 days.
- Responses with abnormally large TXT records relative to the query — data coming back down the tunnel.
- Lens: Best telemetry: Cloud Audit Logs (Admin Activity + Data Access) + Security Command Center + VPC flow logs. SD-WAN/branch firewall logs forwarded centrally; local DHCP/DNS logs for device attribution.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to NAC or port-level logs identifying which device was on which port during the incident.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Cloud Audit Logs: setIamPolicy, storage.setIamPermissions, compute inserts, and console logons and Security Command Center findings; Forseti/Config Validator drift reports where deployed; run `gcloud logging read 'protoPayload.methodName:"SetIamPolicy"' --limit 20 --format='table(timestamp, protoPayload.authenticationInfo.principalEmail, resourceName)'` then `gcloud scc findings list organizations/$ORG_ID --filter='state="ACTIVE"' --limit 15`.
3. **Analyze.** Decode a sample of tunneled queries/responses in a sandbox to determine direction and content: C2 instructions, exfiltrated data, or both. Then: Identify patient zero by earliest query timestamp, then hunt laterally: tunneling tools are often deployed to multiple hosts.
4. **Contain and harden.** Force all DNS through logged, filtered resolvers; block direct port-53 egress from endpoints and alert on non-standard DNS ports. Asset layer: Organization policies: no public buckets, no default SA use, OS Login on; deny unapproved APIs. Environment layer: Standardized branch firewall policy deployed as code; no local admin exceptions.
5. **Document and improve.** Assign RACI for each procedure step (who detects, who contains, who communicates) and rehearse it quarterly. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Blocking the domain without finding the implant — the attacker rotates domains faster than you blocklist.
- Ignoring DNS over HTTPS (DoH): tunneled traffic inside DoH is invisible to passive DNS monitoring — log at the endpoint.
