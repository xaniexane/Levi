# DNS Fast-Flux Defense for Kubernetes Clusters in GCP Cloud (Developing Maturity)

## Purpose

Fast-flux networks rotate DNS answers across many compromised hosts every few minutes, making malicious infrastructure hard to takedown. Defenders detect the flux pattern itself: low TTLs, high answer churn, and geographically scattered A records. Applies to Kubernetes Clusters in GCP Cloud at Developing maturity.

## When to use

- DNS answers with TTLs under 300 seconds rotating across dozens of IPs in unrelated ASNs and countries for a single domain.
- Short-lived domains (registered days ago) resolving to residential or compromised-server IPs with no legitimate business relationship.
- Endpoint connections to flux domains correlating with malware detonations or phishing kit infrastructure.
- Lens: Best telemetry: Kubernetes audit logs + container runtime logs + admission-controller denials. Cloud Audit Logs (admin + data access) exported to a locked-down logging project.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to Security Command Center findings and VPC flow logs centralized.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in API-server audit log (who created pods/bindings/secrets, from where) and Kubelet/container runtime logs and image pull histories per node; run `kubectl audit2rbac --filename=audit.log 2>/dev/null | head; kubectl get clusterrolebindings -o wide | head -20` then `kubectl get pods -A -o json | python3 -c "import json,sys; [print(p['metadata']['namespace'], p['metadata']['name'], p['spec'].get('hostNetwork'), p['spec'].get('hostPID')) for p in json.load(sys.stdin)['items']]" | head -30`.
3. **Analyze.** Profile the flux: record TTL, unique IPs per hour, ASN/country spread, and name-server patterns to fingerprint the specific flux service or kit. Then: Pivot from the domain to find sibling infrastructure: shared name servers, registration patterns, and certificate overlaps.
4. **Contain and harden.** DNS response policy zones (RPZ) blocking confirmed flux domains, plus alerting on sub-300s TTL answers at the resolver. Asset layer: Least-privilege RBAC, Pod Security Standards enforced, no privileged pods, image signing/verification. Environment layer: Organization policies constraining public exposure, API enablement, and service-account key creation.
5. **Document and improve.** Assign RACI for each procedure step (who detects, who contains, who communicates) and rehearse it quarterly. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Blocking individual flux IPs — they churn in minutes; block the domain pattern and the detection logic instead.
- Confusing legitimate CDN behavior (low TTL, many IPs) with flux; require the ASN-scatter plus short-domain-age combination.
