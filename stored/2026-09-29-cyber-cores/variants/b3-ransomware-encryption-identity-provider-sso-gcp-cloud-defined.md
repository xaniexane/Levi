# Ransomware Encryption Defense for SSO Identity Providers in GCP Cloud (Defined Maturity)

## Purpose

Ransomware encrypts files and demands payment, usually after days of dwell time spent disabling recovery. Speed of isolation decides whether you lose one host or the fleet. Never pay without a deliberate, documented decision process. Applies to SSO Identity Providers in GCP Cloud at Defined maturity.

## When to use

- EDR fires on mass file rename/extension changes, vssadmin delete shadows, bcdedit recovery disabling, or known ransomware process names within seconds of each other.
- Ransom notes (README, DECRYPT files) appearing in multiple directories, wallpaper changes, or a sudden burst of encrypted file extensions across shares.
- Precursor activity in the prior 72 hours: disabled EDR tamper protection, cleared event logs, or backup job failures and backup-server logons from unusual accounts.
- Lens: Best telemetry: authentication logs with MFA detail + app-assignment changes + federation trust changes. Cloud Audit Logs (admin + data access) exported to a locked-down logging project.

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to Security Command Center findings and VPC flow logs centralized.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Authentication logs per application (success/failure, MFA method, device, location) and Application assignment and provisioning logs; new SSO integrations; run `# conceptually (IdP APIs differ):` then `idp-cli logs auth --user <upn> --last 7d --format table | head -25`.
3. **Analyze.** Identify the variant from the note text, extension, and ransom portal; check public decryptor availability before any recovery decision — some variants have free decryptors. Then: Reconstruct the entry vector (phishing, exposed RDP/VPN, software vulnerability) and the dwell timeline: first access, privilege escalation, backup targeting, detonation.
4. **Contain and harden.** Immutable, offline-tested backups with alerting on backup tampering; network segmentation so one host cannot reach all shares. Asset layer: Phishing-resistant MFA default, sign-on policies per app risk, session lifetime limits. Environment layer: Organization policies constraining public exposure, API enablement, and service-account key creation.
5. **Document and improve.** Map each detection signal to the relevant MITRE technique and confirm coverage in the detection engineering backlog. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Rebuilding from backups that the attacker already found and poisoned — verify backup integrity and isolation first.
- Paying the ransom without confirming the decryptor works and without legal/regulatory review of sanctions exposure.
