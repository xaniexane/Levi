# Ransomware Encryption Defense for Docker Hosts in Remote Workforce (Foundational Maturity)

## Purpose

Ransomware encrypts files and demands payment, usually after days of dwell time spent disabling recovery. Speed of isolation decides whether you lose one host or the fleet. Never pay without a deliberate, documented decision process. Applies to Docker Hosts in Remote Workforce at Foundational maturity.

## When to use

- EDR fires on mass file rename/extension changes, vssadmin delete shadows, bcdedit recovery disabling, or known ransomware process names within seconds of each other.
- Ransom notes (README, DECRYPT files) appearing in multiple directories, wallpaper changes, or a sudden burst of encrypted file extensions across shares.
- Precursor activity in the prior 72 hours: disabled EDR tamper protection, cleared event logs, or backup job failures and backup-server logons from unusual accounts.
- Lens: Best telemetry: Docker daemon logs + host auditd + container stdout/stderr shipped centrally. EDR on every endpoint as the primary sensor (no corporate network tap for remote hosts).

## Prerequisites

- Written authorization from the asset owner and incident commander before active containment.
- Access to VPN/ZTNA access logs and SaaS/IdP sign-in logs as the network-visibility substitute.

## Procedure

1. **Authorize and scope.** Open a ticket, confirm written authorization, and preserve evidence before changing anything.
2. **Detect and collect.** Hunt the signals above in Docker daemon log (container create/start with full flags), docker events history and Container image digests and layer histories (docker history) versus expected digests; run `docker ps --format '{{.Names}} {{.Image}}' ; echo ---; docker events --since 24h --until 0s 2>/dev/null | tail -20` then `docker inspect $(docker ps -q) --format '{{.Name}} privileged={{.HostConfig.Privileged}} mounts={{.Mounts}}' 2>/dev/null`.
3. **Analyze.** Identify the variant from the note text, extension, and ransom portal; check public decryptor availability before any recovery decision — some variants have free decryptors. Then: Reconstruct the entry vector (phishing, exposed RDP/VPN, software vulnerability) and the dwell timeline: first access, privilege escalation, backup targeting, detonation.
4. **Contain and harden.** Immutable, offline-tested backups with alerting on backup tampering; network segmentation so one host cannot reach all shares. Asset layer: No --privileged, no host socket mounts except for explicit agents, user namespaces enabled, read-only root filesystems. Environment layer: Zero-trust access: device compliance + MFA per application, not per network.
5. **Document and improve.** Define one escalation trigger in advance (e.g., confirmed credential theft, more than 3 hosts) that moves the case from analyst to incident commander. Record the timeline, indicators, actions taken, and lessons learned.

## Expected outputs

- Scoped timeline; affected assets, accounts, and data with containment status each.
- Hardening verified effective; detection improvements filed.

## Pitfalls

- Rebuilding from backups that the attacker already found and poisoned — verify backup integrity and isolation first.
- Paying the ransom without confirming the decryptor works and without legal/regulatory review of sanctions exposure.
